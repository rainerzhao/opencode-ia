# 团队 AI 工作台完整项目设计

**状态：** 已批准总体方向，等待书面设计复核  
**日期：** 2026-09-01  
**开发环境：** 当前 macOS 电脑  
**生产目标：** 公司内网单台 Linux 服务器，约 15–20 名团队成员通过浏览器访问

## 1. 项目目标

将现有 `/Users/yenini/Desktop/opencode-ia` 原型改造成可开发、可测试、可迁移、可部署、可维护的团队级 AI 工作台。

工作台服务于非研发解决方案团队，覆盖 GPU 选型、信创迁移、架构评审和售前方案等场景。产品的核心闭环是：

1. 成员通过私人 AI 对话处理问题。
2. OpenCode 使用管理员授权的模型、团队知识和已发布 Skill 生成结果。
3. 成员人工确认、编辑结果。
4. 经确认的内容发布为团队方案或知识。
5. 团队继续复用并迭代这些资产。

遵循“AI辅助、人工确认”：AI 负责检索、提取、生成和效率提升，成员保留事实核验、风险判断和最终发布责任。

## 2. 明确约束

- 所有模型推理、Agent、Skill 和工具执行必须经过 OpenCode；工作台不得直连模型 API。
- OpenCode 在生产环境使用公司内部、兼容 OpenAI 协议的模型 API。
- 当前 Mac 可使用现有模型 Provider 完成开发和联调；迁移 Linux 时只替换 OpenCode Provider 配置。
- 不接入公司 SSO，采用管理员创建的本地用户名密码账号。
- 不开放用户自行注册。
- 私人对话默认仅本人可见；用户主动发布后才成为团队共享资产。
- 普通成员可以创建、校验和发布 Skill；前期不设置人工逐级审批。
- 内部平台没有 API，不把 MCP 包装内部平台作为本项目依赖。
- 不引入收费商业平台。
- 所有密钥只通过环境变量或运行环境的 Secret 机制注入，不进入代码、数据库、前端、日志或文档。

## 3. 非目标

- 第一版不集成公司 SSO。
- 第一版不引入 Kubernetes、Redis 或独立 PostgreSQL 集群。
- 第一版不建设独立向量数据库；知识检索先使用 SQLite FTS5。
- 第一版不允许用户自行填写模型 API 地址或密钥。
- 第一版不自动将私人对话发布到团队知识库。
- 第一版不向 OpenCode 暴露任意主机文件系统访问权限。

## 4. 总体架构

系统采用 React/Vite 前端、模块化 Express 后端、SQLite 与文件数据目录、OpenCode 常驻服务的组合。

```text
React 工作台
登录、对话、知识、方案、Skill、管理后台
                         ↓
Express 业务后端
认证权限、会话编排、知识检索、版本、审计
          ↓                              ↓
SQLite + 数据目录                  OpenCode Gateway
结构化元数据与全文索引              会话映射、事件流、超时、取消
Markdown、附件、Skill 版本                  ↓
                                  OpenCode 常驻服务
                                  Agent / Skill / Tool
                                           ↓
                                  内部模型 Provider
```

### 4.1 职责边界

工作台后端负责：

- 登录、角色、权限和服务端 Session。
- 用户私人会话与 OpenCode Session 的映射。
- 确定性知识检索、引用组织和发布流程。
- 知识、方案、Skill 的版本、回收站和审计。
- OpenCode 健康检查、并发控制、超时和错误映射。

OpenCode 负责：

- 模型 Provider 和模型调用。
- Agent 上下文和多轮会话。
- Skill 发现与执行。
- 工具调用和 AI 生成过程。

前端负责：

- 页面交互和状态展示。
- 流式响应与执行过程展示。
- 用户提交、编辑和人工确认。
- 仅在浏览器保存主题等非敏感偏好，不保存关键业务数据。

### 4.2 代码边界

目标代码结构：

```text

  web/                 React/Vite 前端
```

## 5. 身份、权限和隐私

### 5.1 账号体系

- 系统仅有管理员和普通成员两个角色。
- 首次启动通过命令行创建首位管理员，不提供公开默认账号或密码。
- 账号由管理员创建、停用、重置密码和分配角色。
- 密码使用 Node.js `scrypt`、独立随机盐和安全参数哈希。
- 登录 Session 使用高熵随机 Token；数据库只保存 Token 哈希。
- Cookie 使用 `HttpOnly`、`SameSite=Lax`，生产 HTTPS 下启用 `Secure`。
- 修改密码、停用账号或管理员强制退出后，撤销相关 Session。
- 登录失败执行按账号和来源 IP 的限速与短时锁定。

IP 不作为用户身份。Linux 生产环境可以在 Nginx 层限制公司内网网段，但审计身份始终来自登录账号。

### 5.2 权限

普通成员可以：

- 管理自己的私人对话。
- 从管理员授权列表选择模型。
- 创建、编辑、上传和版本化知识。
- 创建、编辑和发布方案。
- 创建、校验、发布、升级、停用或归档自己的 Skill。
- 查看本人相关审计记录。

管理员额外可以：

- 管理账号、角色和会话。
- 管理模型目录与默认模型。
- 管理全部知识、方案、导航和 Skill。
- 调整 Skill 校验规则。
- 查看系统审计、健康、任务和备份状态。

所有永久删除和高风险恢复操作只允许管理员执行并要求再次确认。

### 5.3 隐私

- 私人对话默认仅所有者可见。
- 管理员默认只能查看模型、时间、状态、耗时和用量等调用元数据。
- 用户点击“沉淀为方案”或“发布到知识库”，并人工确认后，内容才成为团队共享资产。
- 安全事件下查看私人正文必须走单独受审计操作。
- 日志不得记录密码、Cookie、Token、API Key 和敏感请求头。

## 6. AI 对话与 OpenCode

### 6.1 常驻服务

- OpenCode 以常驻服务运行，不为每条消息冷启动完整环境。
- 工作台使用一个常驻 Gateway 控制面和多个常驻 Worker 执行面；Mac 默认 2 个 Worker，Linux 初始 2 个并根据压测调整到 2–4 个。
- Worker 不与用户固定绑定。一个 Worker 可承载多个逻辑 Session，但同一 Session 同时只执行一个任务。
- Gateway 使用 `Conversation → OpenCode Session → Worker` 粘性映射，实施全局并发、单用户并发和按用户公平排队。
- 单机首版使用 SQLite 持久化映射与任务状态，不引入 Redis 或 Kubernetes。
- OpenCode 只监听回环地址；工作台后端是唯一业务调用方。
- OpenCode Gateway 封装具体调用协议。优先使用当前 OpenCode 版本支持的服务或 SDK 接口；若需要使用 `opencode run --attach`，必须参数化调用，禁止 Shell 字符串拼接。
- Gateway 对上层暴露稳定的创建会话、发送消息、订阅事件、停止运行、恢复会话和健康检查接口。

### 6.2 会话隔离

- 每个工作台 Conversation 绑定唯一 OpenCode Session ID。
- 每个会话使用独立工作目录，避免用户间文件和上下文串联。
- 共享知识和已发布 Skill 只读提供给 AI 执行环境。
- 对共享资产的正式修改只能通过工作台业务接口完成。
- 服务端执行全局并发上限与单用户并发上限。
- 浏览器断开时按任务策略取消或继续；交互式生成默认取消。

### 6.3 模型目录

- Provider、API 地址和密钥由管理员在 OpenCode 运行环境配置。
- 工作台数据库只保存可公开的模型 ID、显示名、描述、排序、状态和默认标记。
- 普通成员只能选择管理员授权模型，不能提交 API 地址或密钥。
- Mac 与 Linux 的模型 Provider 可以不同，工作台业务代码保持不变。

### 6.4 用户体验

- 支持连续多轮对话、停止、重试、重命名和删除。
- 流式展示正文、工具调用、Skill 使用、知识引用、完成和错误状态。
- 原“OpenCode 终端”改为只读“执行过程”面板，不接受伪终端输入。
- FAQ 使用同一 OpenCode 链路，采用受限知识范围和简洁回答规则。

## 7. 知识库与方案闭环

### 7.1 知识存储与检索

- Markdown 是知识正文标准格式。
- SQLite 保存标题、分类、标签、作者、状态、版本和全文索引。
- 第一阶段使用 SQLite FTS5 检索标题、标签和正文。
- 检索片段作为确定性上下文交给 OpenCode，由 OpenCode 完成答案生成。
- 回答展示可点击来源和引用片段；无可靠命中时明确提示未命中团队知识。
- 后续可以在不改变业务接口的情况下增加本地向量召回。

支持 Markdown、TXT、PDF、DOCX、JSON 和 CSV。上传后保留原文件，异步提取文本、生成 Markdown 表示并建立索引。解析失败不丢失原文件，并显示任务状态和失败原因。

### 7.2 版本和删除

- 每次正式保存生成不可变版本。
- 支持查看版本历史、差异和回滚。
- 删除先进入回收站，默认 30 天后清理。
- 文件写入与数据库记录通过临时文件、校验、原子替换和事务保持一致。

### 7.3 方案闭环

1. 用户从私人对话点击“沉淀为方案”。
2. OpenCode 根据已选消息生成结构化草稿。
3. 用户编辑并确认需求背景、约束、推荐架构、步骤和风险。
4. 用户发布到团队方案库。
5. 已发布方案可进一步转换为知识文档。

方案记录使用的模型、知识引用和 Skill，但不得复制密钥或敏感系统提示。

## 8. Skill 中心

Skill 采用轻量自助发布：

```text
草稿 → 自动校验 → 创建者发布 → 团队启用 → 升级 / 回滚 / 停用 / 归档
```

自动校验至少包括：

- `SKILL.md` 元数据、目录结构和必需文件。
- 名称冲突和版本号。
- 明文密钥和敏感信息扫描。
- 路径逃逸、明显危险命令和越界文件访问。
- 基础运行或验收测试。

发布规则：

- 只有校验通过的不可变版本可以发布。
- 发布采用原子切换；失败时继续使用旧版本。
- 创建者可以管理自己的 Skill；管理员可以管理全部 Skill。
- 删除默认变为归档或回收站；永久删除只允许管理员。
- 每次发布、升级、停用和回滚记录操作者、版本和校验报告。
- 发布完成后必须验证 OpenCode 能发现新版本；失败则回滚 active 指针。

## 9. 数据模型

SQLite 至少包含：

- `users`
- `login_sessions`
- `conversations`
- `messages`
- `model_catalog`
- `knowledge_documents`
- `knowledge_versions`
- `solutions`
- `solution_versions`
- `skills`
- `skill_versions`
- `navigation_links`
- `audit_logs`
- `system_jobs`

数据库启用外键、WAL 和版本化迁移。升级前执行备份；迁移失败时停止启动，不带着半完成结构继续服务。

## 10. 安全设计

- 所有请求输入使用共享 Schema 校验。
- 所有文件路径必须解析并验证位于配置的数据根目录内。
- 进程调用必须使用可执行文件和参数数组，不经过 Shell。
- 上传同时验证扩展名、MIME、大小和真实文件类型，保存为不可执行权限。
- URL 抓取仅允许 HTTP/HTTPS，并拒绝回环、链路本地、云元数据和未授权内网地址；管理员维护允许域名。
- 前端输出进行上下文安全编码，Markdown 使用受控渲染和 HTML 清洗。
- 状态修改接口具备 CSRF 防护。
- OpenCode 工作目录、可用工具和文件边界按最小权限设置。
- 应用、OpenCode、数据目录和密钥配置分离。
- 项目执行自动密钥扫描；当前交接文档中的暴露 Key 必须清除并在 Provider 侧轮换。

## 11. 错误处理与可观测性

- API 使用统一错误代码、用户可读信息和追踪 ID。
- OpenCode 不可用时拒绝新生成请求并显示真实服务状态，不返回模拟答案。
- 模型超时允许重试，保留原消息，不重复创建共享资产。
- 知识索引失败时正文保留并标记待处理。
- Skill 发布失败时旧版本继续生效。
- 后台任务记录状态、尝试次数、错误和下次执行时间，不无限重试。
- 创建和发布接口支持幂等，避免重复点击产生多份记录。
- 结构化日志具备脱敏、轮转和追踪 ID。
- 健康检查分别覆盖应用、数据库、文件目录和 OpenCode。

## 12. 数据保留、备份和恢复

默认值均可通过环境变量调整：

- 审计日志保留 365 天。
- 私人对话保留至用户主动删除。
- 回收站保留 30 天。
- 每日备份，保留最近 30 份日备份。

备份覆盖 SQLite、知识、附件、Skill、配置模板和版本元数据，不包含明文密钥。必须提供自动备份、手工备份、恢复到新实例和恢复验证流程。

## 13. 开发与部署

### 13.1 Mac

- 使用 npm workspace 启动前后端。
- OpenCode 以独立常驻服务运行。
- 开发数据库和数据目录与真实数据分离。
- 浏览器完成桌面、笔记本和窄屏验收。

### 13.2 Linux

- 推荐 Docker Compose 部署工作台与 OpenCode。
- Nginx 提供 HTTPS、反向代理和可选内网网段白名单。
- 容器和服务以非 root 用户运行。
- 数据目录使用持久卷。
- OpenCode Provider 配置公司内部兼容 OpenAI 协议的模型 API。
- 支持健康检查、日志轮转、备份、迁移、升级和恢复。

同时保留非容器 npm/进程管理器部署说明，避免 Docker 在目标环境不可用时阻断上线。

## 14. 实施阶段

### 阶段 0：项目基线与安全止血

清除密钥、建立配置规范、版本控制、备份和测试基线，修复命令注入、路径逃逸、任意 URL、上传和并发问题。

### 阶段 1：工程重构与账号体系

建立 workspace、React、模块化 Express、SQLite、认证、权限、审计和统一错误处理，迁移现有 UI。

### 阶段 2：OpenCode 核心链路

完成常驻服务、Gateway、会话隔离、流式事件、停止、超时、恢复、并发和模型目录。

### 阶段 3：知识库与方案闭环

完成文档版本、附件解析、FTS5、知识引用、方案草稿、人工确认和 FAQ 正式链路。

### 阶段 4：Skill 中心与管理后台

完成 Skill 校验、自助发布、版本、回滚、OpenCode 发现验证，以及用户、模型、健康、审计和任务后台。

### 阶段 5：生产化与迁移准备

完成容器、Nginx、健康、日志、备份恢复、Linux Provider 模板、部署升级和故障排查文档。

各阶段必须保持应用可启动、可测试、可回退，不同时并行重写所有子系统。

## 15. 测试与验收

采用测试先行：行为修改必须先写能正确失败的测试，再实现最小代码使其通过。

- 单元测试：权限、路径、密码、检索、版本和 Skill 校验。
- API 集成测试：临时 SQLite 与临时数据目录上的真实接口。
- OpenCode 契约测试：模拟服务覆盖协议，真实 OpenCode 执行可开关冒烟测试。
- WebSocket 测试：事件流、断线、停止、超时和会话隔离。
- 前端测试：登录、权限、状态和错误提示。
- Playwright：完整用户流程与浏览器布局。
- 安全测试：越权、路径逃逸、命令注入、XSS、CSRF、上传、SSRF 和密钥扫描。
- 并发测试：20 个登录用户的独立对话，无串话且遵守并发上限。
- 恢复测试：备份、恢复到新测试实例并核对数据。

普通自动化测试不调用真实付费模型；真实模型测试仅在明确启用时运行。

## 16. 完成交付标准

- Mac 上完整应用真实跑通。
- 同一代码库可配置迁移到单台 Linux。
- 所有自动化测试、语法检查和构建通过。
- 浏览器完整交互验收通过，无关键布局溢出。
- 项目不存在明文密钥和已知高风险入口。
- 20 个用户会话隔离验证通过。
- OpenCode、知识库、Skill 和方案闭环真实可用。
- Skill 发布后能被 OpenCode 发现，失败可回滚。
- 备份能够恢复到新测试实例。
- 初始化、开发、部署、升级、备份、恢复和排障文档齐全。
- 不使用占位用户、虚假操作记录或未经确认的内部 URL。
- 外部 Linux 环境和内部模型 API 在未取得真实条件前明确标记为待生产验证，不能宣称已上线。

## 17. 项目管理与质量门禁

每个阶段遵循：

```text
需求基线 → 逐文件计划 → 测试先行 → 实现 → 任务审查
→ 安全/质量验收 → 浏览器验收 → 阶段报告
```

- 不在未审查的情况下跨阶段推进。
