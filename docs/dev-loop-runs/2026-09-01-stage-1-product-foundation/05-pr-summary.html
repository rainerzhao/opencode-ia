Stage 1A–1C 产品底座评审摘要

从持久账号与安全 Session，推进到全业务认证、私有隔离与可追溯执行

STATUS · STAGE 1C PASS DATE · 2026-09-02 BRANCH · MAIN
TL;DR
Stage 1A 建立 SQLite 与审计数据底座；Stage 1B 接通账号、Cookie/CSRF 和 Session 控制；Stage 1C 将全部业务 REST/WebSocket 切换到真实账号身份，加入默认私有、写操作审计、跨站 Socket 防护和撤销重验证。所有 AI 执行仍只经过 OpenCode，仓库不保存 Provider 密钥。前端登录仍在 Stage 1D，因此当前仍不能作为内网多用户生产系统开放。

01本次解决的问题

BOUNDARY
统一认证
REST 与 WebSocket 都从服务端 Session 获得身份，匿名访问在业务入口即被拒绝。
PRIVACY
默认私有
方案和知识草稿绑定创建者，成员互不可见；共享知识与本人内容安全合并。
TRACE
操作追踪
关键写入和 OpenCode 执行绑定真实用户，只记录资源与长度等脱敏元数据。

03测试与审查

  • 真实边界。使用临时 SQLite、真实 HTTP 监听、Cookie 与 CSRF 请求完成集成测试，不以 mock 代替认证链路。
  • 错误一致。不存在的账号、错误密码和停用账号使用同一无泄漏错误；Session 失效返回稳定错误码。
  • 审查修复。成功登录不再清空来源 IP 的失败累计，避免持有任意有效账号后绕过 IP 维度限速。
  • 缓存边界。认证和管理员响应统一设置 Cache-Control: no-store。
  • 权限回归。匿名、跨成员、异源 WebSocket 和撤销后继续执行均由真实 HTTP/WebSocket 用例覆盖。
  • 文件边界。私人目录和文件强制 0700/0600，不依赖运行系统的默认 umask。
  • 验收结果。npm test 111/111，通过 53 个 JS 文件语法检查和零发现密钥扫描。
  • 发布门禁。npm test、npm run check、npm run security:scan 和 git diff --check 在提交前重新执行。

04残余边界与下一步

NOT PRODUCTION READY
Stage 1C 已完成后端业务权限切换，但现有静态前端尚未提供登录和账号管理界面。直接打开页面无法完成受保护业务流程；在 Stage 1D–1E 完成前不能对真实多用户开放。

Stage 1D 将接入前端登录、当前用户、退出和管理员账号管理，并完成桌面/手机真实浏览器验收。随后 Stage 1E 完成 React/Vite 迁移和 Stage 1 总验收。
